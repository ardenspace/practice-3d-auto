## 확정된 렌더 설정 (실측 기반)

프레임당 **1.28초**(1080p). 계획이 전제한 0.75초는 훨씬 단순한 장면에서 나온 값이라 맞지 않았다.

| 항목 | 값 | 근거 |
|---|---|---|
| TAA 샘플 (`--samples`) | **32** | 64샘플 대비 절반 시간. 사용자가 두 판본을 보고 32를 선택 |
| `PARAMS["fog"]["samples"]` | 64 | 128 대비 화면 차이 없이 28% 절약 |
| `PARAMS["fog"]["tile_size"]` | **"2"** | "4"로 낮추면 빛기둥에 마름모 격자 무늬가 돌아온다. 절대 낮추지 말 것 |
| `shadow_resolution_scale` | 0.5 | 1.0 대비 화면 차이 없이 18% 절약 |
| `shadow_step_count` | 3 | 위와 같음 |
| 루프 클립 길이 | **90초** | 설계는 2~3분이었으나 렌더 예산 때문에 줄였다 |

고유 프레임 약 11,040장 → **약 4시간**. 실측 중 Chrome Remote Desktop과 VS Code가 GPU를 함께
쓰고 있었으므로, 실제 밤샘 렌더 때 닫으면 더 빨라진다.

렌더 비용의 구조(빈 장면 1080p 실측): 1샘플 0.061초, 16샘플 0.334초, 64샘플 1.237초. 샘플 수가

## 이번 세션에서 내린 판단 (계획을 벗어난 것들)

1. **`marble` 이름 충돌** — 유리구슬 오브젝트와 4번 카메라가 둘 다 `marble`이라 Blender가 카메라를
   `marble.001`로 개명했다. 구슬을 `marble_glass`로 바꾸고 카메라가 `marble`을 갖게 했다.
   계획 Task 2의 테스트 코드에서 오브젝트 이름 목록도 그에 맞게 고쳤다.
2. **커밋 트레일러** — 계획은 `Claude Fable 5.1`을 지정하지만 각 서브에이전트의 하네스가 지정한
   트레일러를 쓴다.
3. **워크트리를 만들지 않았다** — 사용자가 `pilot-gates-1-2`를 그대로 쓰라고 지시했다.
   `episodes/pilot-test/shot01_layered.json`의 커밋되지 않은 변경은 손대지 않았다. 앞으로도 그대로 둘 것.
4. **`render_clip`의 재실행 안전** — 계획 코드는 `out_path.exists()`만 봤다. mp4를 스트리밍으로 쓰는
   중에 죽으면 손상된 파일이 완료로 오판된다. 임시 위치에 렌더한 뒤 `os.replace`로 옮기게 고쳤다.
5. **관문 승인 전에 커밋한다** — 계획 Task 3 Step 6은 승인 후 커밋이지만, 리뷰가 diff를 필요로 하고
   컨텍스트가 압축됐을 때 복구 지점이 사라지므로 먼저 커밋한다.
6. **소품과 절차적 재질을 추가했다** — 관문 1에서 사용자가 "형태가 너무 단순하다"고 해서, 세 수준을
   제시하고 사용자가 "소품 추가 + 절차적 재질"을 선택했다. 설계 3.3의 "텍스처 이미지는 쓰지 않는다"는
   이미지 파일 금지이며 절차적 노이즈 노드는 이미지가 아니라고 해석했다. 형태 규칙(기본 도형, 단색
   재질)은 유지한다. 서브디비전과 디스플레이스먼트는 렌더 예산 때문에 금지한다.
7. **루프 클립을 90초로 줄였다** — 설계 4.2절은 2~3분이라고 했다. 카메라 네 자리가 순환하므로 같은
   그림이 돌아오는 주기는 약 7분이다. 완성본에서 반복이 눈에 띄면 다시 길게 뽑아야 한다.
8. **PNG 시퀀스 렌더를 도입했다** — 4시간짜리 렌더가 중간에 죽어도 프레임 단위로 이어가기 위해서다.

## 앞으로 조심할 것

- **가로등 조명 위치**: `PARAMS["lamp"]`의 `spot_z`/`fill_z`는 기둥(z 0~`post_height`) 안에 들어가면
  안 된다. 들어가면 자기 형상에 가려 빛이 한 줄기도 나오지 않는다. 전구 구체 안쪽인 것은 괜찮다.
  전구가 `visible_shadow = False`이기 때문이다. 이 문제로 관문 1에서 한참 헤맸다.
- **월드 배경 색**: AgX 톤매핑이 어두운 값을 크게 들어 올린다. 팔레트의 `sky`는 지면 알베도 `night`
  보다 훨씬 낮아야 한다(현재 0.0016 대 0.010). 이 둘을 같은 값으로 두면 밤이 흐린 낮처럼 보인다.
- **나무 가지**: 길이를 캐노피 폭에서 역산한다(`branch_reach_factor_range`). 나무 높이에 비례시키면
  가지가 캐노피 밖으로 삐져나와 벌레 다리처럼 보인다.
- **나무 난수**: 나무마다 독립된 `random.Random(f"{seed}-{i}")`를 쓴다. 하나를 공유하면 나무 하나의
  값을 바꿀 때 다른 나무의 형태까지 밀려서 바뀐다.
- **기존 2.5D 코드를 건드리지 말 것**: `pipeline/depth.py`, `pipeline/layers.py`, `pipeline/render.py`,
  `pipeline/blender/parallax_scene.py`, `episodes/pilot-test/`와 관련 테스트.
- **`git add -A`나 `git commit -a`를 쓰지 말 것**: `episodes/pilot-test/shot01_layered.json`에
  커밋되지 않은 변경이 있고 그대로 두어야 한다.

## 미뤄 둔 지적 (최종 리뷰에서 판단할 것)

- 계획이 준 테스트 코드의 PIL `getdata` 사용으로 DeprecationWarning 2건이 테스트 출력에 남는다.
- `build_puddles`의 물웅덩이 z(0.103/0.253)와 도로 점선 z(0.105)가 하드코딩이다. 도로·인도 두께를
  바꾸면 따로 갱신해야 한다. 다른 소품은 `_road_top`/`_sidewalk_top` 헬퍼로 일원화되어 있다.
- `make_material`에 넘긴 정적 `roughness`가 `add_procedural_roughness`의 링크에 덮여 죽은 값이 된다.
- `branch_reach_factor_range` 상한 0.9와 `lobe_w_factor_range` 하한 0.75의 여유가 좁다
  (실측 margin 최소 0.030m). 상한을 올리면 재검증이 필요하다.
- `common.parse_scene_args`의 `--event`에 `choices` 검증이 없다.
- `_render_frames_to_dir`의 독스트링은 `frames_dir`가 미리 있어야 한다고 하지만 강제되지 않는다
  (Blender가 출력 경로를 자동으로 만든다).
- 장면 스크립트의 `--out` 도움말이 애니메이션 모드에서 PNG 파일명 접두어를 뜻한다는 사실을 반영하지
  않는다. 계획 문서의 CLI 계약 절은 갱신됐다.
- 안개 `samples` 128→64 변경이 PNG 시퀀스 커밋(`6e6f58f`)에 함께 담겼다. 별도 커밋으로 나눴어야 했다.

## 파이프라인이 지금 어떻게 도는가

애니메이션 렌더는 이제 두 단계다. `render_clip`이 `<out>.frames/` 디렉터리에 PNG 연속 이미지를
만들고(Blender, `use_overwrite=False`로 이미 있는 프레임은 건너뜀), ffmpeg으로 mp4를 만든 뒤
PNG 디렉터리를 지운다. 최종 mp4는 임시 위치에 만들어 `os.replace`로 옮기므로 손상된 산출물이
완료로 오판되지 않는다. PNG 디렉터리는 임시 위치 **바깥**에 있어서 렌더가 죽어도 남는다.

재개할 때는 가장 번호가 큰 PNG 하나를 무조건 지우고 시작한다. 그 프레임이 쓰다 만 상태일 수
있기 때문이다. 완성된 프레임이었다면 한 장 다시 렌더하는 비용만 든다.

`--still` 경로는 종전대로 png 한 장을 바로 만든다.
