## 결론

계획의 8개 태스크가 전부 끝났고 관문 1~4를 모두 사용자 승인으로 통과했다. 첫 영상이 완성됐다.

`episodes/dream-bus-stop/final/dream-bus-stop_30min.mp4` — 30분 26초, 1920×1080, 24fps, 무음, 250MB

브랜치 전체 리뷰는 "수정 후 병합 가능"으로 판정했고, 지적을 반영한 뒤(`5aaa6be`) 재리뷰에서 전부
해소를 확인받고 `main`에 fast-forward로 병합했다. 테스트는 59개가 통과한다.

## 완성본의 구조

도입(행성 하강 20초) → `wide` 90초와 `puddle` 120초가 번갈아 돌며 5분마다 버스 통과 30초 →
마무리(행성 상승 20초). 클립 사이는 2초 크로스페이드로 잇는다.

산술로 검증했다. 루프 16개(wide 8×90 + puddle 8×120 = 1,680초)에 버스 5개(150초)를 끼워 1,830초,
도입·마무리를 더해 클립 23개 1,870초, 크로스페이드 22회×2초를 빼면 1,826초로 실측 길이와 정확히
일치한다.

## 2차 세션에서 내린 판단 (계획을 벗어난 것들)

1차 세션의 판단 1~12는 session-1 문서에 있다. 아래는 2차 세션의 것이다.

### 브리프가 낡아서 고친 것

1. **`build()`를 통째로 교체하지 않았다.** 계획 Task 5가 실은 `build()` 전문은 Task 2~3 시점의
   것이라 관문 1에서 승인받은 `_build_shared_materials`와 `build_leaves` 호출이 빠져 있었다.
   그대로 덮어썼다면 소품과 절차적 재질이 조용히 사라졌을 것이다. 두 줄만 끼워 넣었다.
2. **Task 5의 렌더 수치를 확정값으로 바꿨다.** 계획은 2,880프레임·64샘플이라고 했지만 관문 2에서
   확정된 값은 2,160프레임·32샘플이다.
3. **관문 3 산출물의 파일명을 처음부터 Task 8 규칙(`<scene>_<camera>_<event>.mp4`)으로 맞췄다.**
   1차 세션의 판단 3이 "Task 8에서 이름을 바꾼다"고 했으나, 처음부터 맞추면 그 단계가 없어진다.
   대신 `shots.json`의 wide `duration_s`를 90으로 맞춰야 한다(실제 클립이 90초이므로).
   틀렸을 때의 비용: 파일명뿐이다.
4. **`shots.json`을 확정값으로 썼다.** `samples` 32(계획은 64), wide `duration_s` 90(계획은 150),
   `ambience` 키 없음(사용자가 무음 선택). 64로 두면 렌더가 두 배, 150으로 두면 이미 뽑아 둔
   90초 클립이 버려져 2,160프레임을 다시 렌더한다.

### 코드 품질

5. **PIL `getdata()`를 `get_flattened_data()`로 바꿨다.** Pillow 12.3에서 폐기되어
   DeprecationWarning을 낸다. 새 테스트뿐 아니라 같은 패턴인 기존 두 줄도 함께 고쳐 1차 세션이
   미뤄 둔 지적을 닫았다.
6. **`ccbefd9`(상수 하나 변경)에 별도 리뷰 자리를 붙이지 않았다.** 그 상수가 옳은지는 "화면이
   `planet_near_a.png`처럼 보이는가"인데 사용자가 바로 그 이미지를 보고 골랐으므로 이미 검증됐다.
   틀렸을 때의 비용: 상수 하나가 리뷰 한 단계를 건너뛴다. 최종 리뷰가 함께 본다.

### 화면을 보고 고친 것

7. **`marble` 카메라의 목표점을 결함으로 판단하고 사용자에게 묻지 않고 고쳤다.**
   유리구슬 중심이 `(0.3, 5.0, 0.61)`인데 카메라 목표점이 `(0.3, 5.0, 0.95)`로 0.34m 위를 향했다.
   시선 축에서 구슬까지의 각도가 17.1°인데 60mm 렌즈의 세로 반화각이 9.6°라 구슬이 프레임 밖이었다.
   `build_cameras`가 이 카메라에만 `focus_target=marble_glass`를 넘기는 것으로 보아 구슬을 담는 것이
   의도였으므로, 취향 선택이 아니라 피사체가 화면에 없는 결함으로 보았다.
8. **행성 근접 컷 거리를 13.7m에서 25.9m로 늘렸다(사용자가 A안 선택).**
   40mm 렌즈의 가로 화각 48.5°에 행성 반지름 10이면 거리 13.7m에서 행성이 화면을 96° 덮어
   화면 전체가 표면이 된다. 화면을 채우면서 가장자리에 별이 남는 거리가 약 26m다.
9. **`marble`과 `shelter`를 이번 회차에서 뺐다(사용자 선택).** 밤샘 렌더 전 스틸 확인에서 정했다.
   `marble`은 목표점을 고친 뒤에도 유리가 불투명한 흰 덩어리로 나와 눈알처럼 보였고, `shelter`는
   안개 너머 30m를 보느라 대비가 낮았다. 카메라 정의 자체는 `bus_stop.py`에 남아 있다.
   새로 렌더할 프레임이 11,040장에서 3,840장으로 줄었다.
10. **루프 자리가 둘만 남아 반복 주기가 7분에서 3분 30초로 짧아졌지만 그대로 진행했다.**
    잠자기용 앰비언트 영상은 한 화면을 몇 시간씩 반복하는 것이 통상적이다. 완성본에서 반복이
    느껴지면 `puddle` 클립만 길게 다시 뽑으면 되고 그때도 `wide`는 재사용된다.
    틀렸을 때의 비용: `puddle`을 120초 늘릴 때마다 2,880프레임, 약 61분.

### 최종 리뷰 대응

11. **매니페스트에 하위 호환을 넣었다.** 리뷰어는 "매니페스트가 없으면 예외"를 제안했지만, 그러면
    이미 승인받은 클립 5개에 매니페스트가 없어 `run_episode`를 다시 돌리는 즉시 전부 예외가 난다.
    매니페스트가 없으면 경고만 하고 재사용하되, 있는데 값이 다르면 예외를 던지게 했다.
    앞으로 만들어지는 클립은 전부 매니페스트를 가지므로 보호 효과는 그대로다.
12. **리뷰어가 "미뤄도 됨"으로 분류한 것 중 한두 줄짜리는 함께 고쳤다.** README는 만들지 않았다.
    사용자가 요청한 것은 "고칠 거 있으면 고치라"이지 새 문서 작성이 아니다.

## 최종 리뷰가 막은 조용한 실패 두 건

이 파이프라인의 존재 목적("밤새 렌더가 죽어도 이어간다", "회차를 계속 찍어 낸다")에 정확히
어긋나는 경로였다. 앞으로 이 코드를 고칠 때 되돌리지 말 것.

1. **프레임 누락 검출** (`render_shot._encode_frames_to_mp4`).
   ffmpeg의 image2 디먹서는 프레임 번호가 끊기는 지점에서 조용히 멈추고 **종료 코드 0**을 낸다
   (리뷰어가 재현: 10프레임 중 5번을 지우면 exit 0, 결과는 4프레임짜리 mp4). 그러면
   `_atomic_produce`가 그 잘린 파일을 완료로 승격시킨다. 이제 인코딩 전에 프레임 집합을 확인하고
   빠진 것이 있으면 예외를 던진다.
2. **렌더 매니페스트** (`render_shot.render_clip`).
   클립 파일명에 길이·해상도·샘플 수·장면 스크립트 변경이 반영되지 않아서, 다음 회차에서
   `PARAMS`를 고치고 다시 돌리면 아무것도 재렌더되지 않고 옛 클립으로 조립된다. 이제 클립 옆에
   `<클립>.mp4.json`을 남기고 정의가 달라졌으면 예외를 던진다.

## 다음 회차를 만들려면

```bash
source .venv/bin/activate
python -m pipeline.run_episode episodes/<회차 디렉터리>
```

회차 디렉터리에 `shots.json`을 두면 된다. 스키마는 `episodes/dream-bus-stop/shots.json`이 예시다.
`scene`, `resolution`, `fps`, `samples`, `target_minutes`, `event_every_s`, `xfade_s`, 그리고
`intro`/`outro`/`loops`/`events`가 들어간다. `ambience`는 선택이며 없으면 무음이 된다.

중간에 죽으면 같은 명령을 다시 실행하면 된다. 완성된 클립과 프레임은 건너뛴다.

## 앞으로 조심할 것 (1차 세션 문서에 더하여)

- **`git add -A`나 `git commit -a`를 쓰지 말 것.** `episodes/pilot-test/shot01_layered.json`에
  커밋되지 않은 변경이 있고 그대로 두어야 한다. 이 때문에 `git checkout main`도 막히므로,
  `main`을 앞당길 때는 `git branch -f main <브랜치>`를 쓴다(fast-forward일 때만).
- **`PARAMS`를 고친 뒤에는 해당 클립 파일을 지워야 한다.** 매니페스트가 장면 스크립트의 mtime을
  담으므로 이제는 예외가 나서 알려 주지만, 예외를 보면 클립을 지우고 다시 돌리면 된다.
- **프로세스 대기에 `pgrep -f`를 쓸 때 자기 참조를 조심할 것.** 이번 세션에서 대기 스크립트 자신의
  명령줄에 검색 문자열이 들어 있어 스스로를 "실행 중인 렌더"로 잡아내 무한히 기다린 일이 있었다.

## 남은 과제 (최종 리뷰가 미뤄도 된다고 판정한 것들)

- 저장소 최상위에 README가 없다. 위의 "다음 회차를 만들려면"이 그 자리를 임시로 메운다.
- `shots.json`의 이벤트 이름에 검증이 없다. 오타(`"buss"`)가 버스 없는 클립을 조용히 만든다.
  `run_episode`에서 장면별 알려진 이벤트를 검사하는 것이 좋다.
- `make_material(roughness=...)`로 넘긴 정적 값이 `add_procedural_roughness`의 링크에 덮여 죽은
  값이 된다. 독스트링에 경고만 달아 두었다.
- 환경음의 상대 경로 분기와 `FileNotFoundError` 분기가 테스트로 덮이지 않는다. 소리를 켤 때 더할 것.
- 오디오 페이드 3초가 하드코딩이다.
- `run_episode`가 `final/*.mp4`가 이미 있어도 무조건 다시 조립한다. 재실행이 30분 인코딩을 다시 돈다.
